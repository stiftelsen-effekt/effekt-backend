# Timestamps and the DB clock

Production Cloud SQL has the flag `default_time_zone=+02:00`: a fixed offset, no DST. The app's mysql2 pools
(`DAO.ts`, `analysisDbPool.ts`) use `timezone: "+00:00"`, which only tells mysql2 how to convert JS Dates. It
does not set the session zone, so sessions run at +02:00 and `NOW()` is UTC+2.

- **App clock**: a value the app writes from a JS Date is sent as its UTC wall clock and read back unchanged
  (TIMESTAMP columns convert on write and on read with the same session zone, so they round-trip too). These
  are correct and must not be converted.
- **DB clock**: a value filled by `DEFAULT CURRENT_TIMESTAMP`, or by `NOW()` / `CURRENT_TIMESTAMP` in SQL,
  holds the session's wall clock (UTC+2). The pool reads it as UTC, so it shows two hours late.

The local dev DB (`compose.dev.yml`, 127.0.0.1:3307) had `@@global.time_zone = SYSTEM` (UTC), so it didn't
reproduce this. It now starts with `--default-time-zone=+02:00` like production; recreate the `db` container
(`pnpm dev:env:up`) to apply it. The volume is kept.

## How to handle a DB-clock column

- **Read**: `dbClockColumn("T.col")` from `custom_modules/osloDays.ts` selects
  `CONVERT_TZ(T.col, @@session.time_zone, '+00:00') AS col`. It uses the session's own zone, so it stays
  correct if the flag changes. Order by the qualified column (`T.col`), not the alias, to keep indexes.
- **Compare with app instants**: `instantRangeClauses(col, range, "db")` (shifts the bound in SQL). Comparisons
  with `NOW()` / `CURDATE()` (`col > NOW() - INTERVAL 30 DAY`) are in one clock and need nothing.
- **Compare app-clock columns with "now"**: use `UTC_TIMESTAMP()`, not `NOW()`.
- **New columns**: write the value from the app (`new Date()`) instead of relying on a default.

## Comparisons left as they are

- `NOW()` against DB-clock columns (`agreementfeedback` 24-hour window, `initialpaymentmethod` last month,
  intents expiry, AvtaleGiro/Vipps "this month" reports): same clock, correct.
- `DATE(Payment_intent.timestamp)` against `Donations.timestamp_confirmed` (intent status, follow-up job): the
  DB-clock date is Oslo's date in summer, an hour later in winter. Kept so the admin matches the job.
- `CURDATE()` / `YEAR(CURDATE())` against app dates (`VA.paused_until_date`, tax-year queries, cost YTD):
  differ only between 22:00 and 24:00 UTC.
- `AutoGiro_agreement_charges.claim_date > NOW()` (Swedish).
- Legacy REST date filters (`filter.created`, `filter.registered` in the AvtaleGiro, Vipps, donor and
  fundraiser list functions) compare DB-clock columns with app dates without the shift. tRPC uses the
  `createdRange` / `registeredRange` filters, which shift.
- `routes/scheduled.ts` follow-up job reads `Payment_intent.timestamp` unconverted (2 hours off on a
  days-scale check).
- Nightly analysis and the Sheets Apps Script read the DB directly and are outside this change.
